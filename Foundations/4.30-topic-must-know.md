# The 30 Must-Know System Design Concepts (Mental Map & Cheatsheet) 🗺️

> **Core Philosophy:** System design is not an endless dictionary of tools. Every scary interview term fits into **4 Core Territories**. Senior engineers win interviews by connecting concepts across territories and explaining failure trade-offs.

---

## 🧭 1. The 4 Territories Framework (The Indian Railways Analogy)

Think of system design as the **Indian Railways Network**:

```
                       ┌────────────────────────────────────────┐
                       │          SYSTEM DESIGN MAP             │
                       └───────────────────┬────────────────────┘
                                           │
         ┌───────────────────┬─────────────┴──────────────┬────────────────────┐
         ▼                   ▼                            ▼                    ▼
   TERRITORY 1          TERRITORY 2                  TERRITORY 3          TERRITORY 4
   Networking        APIs & Messaging             Databases & Storage  Distributed Systems
 (Tracks & Signals) (Languages & Tickets)        (Vaults & Warehouses)  (Coordination & Chaos)
 • DNS, TCP/UDP      • REST, GraphQL, gRPC        • SQL vs NoSQL        • CAP Theorem
 • Load Balancer     • API Gateway, Rate Limit    • ACID, Indexes       • Consensus (Raft)
 • CDN, Proxies      • Queues, Pub/Sub, Sockets   • Sharding, Caching   • Distributed Locks
```

1. **Territory 1: Networking (Tracks & Signals):** How data physically travels from point A to B.
2. **Territory 2: APIs & Communication (Languages & Timetables):** How services talk, enforce rules, and push messages.
3. **Territory 3: Databases & Storage (Vaults & Freight Yards):** Where data permanently lives, scales, and stays fast.
4. **Territory 4: Distributed Systems (Coordination in Chaos):** How hundreds of separate servers agree on truth during network crashes.
* *Plus 2 Edge Strips:* **Scale Patterns** (Replication, Partitioning) & **Operations** (Observability, Circuit Breakers).

## 🍕 2. The 1-Request Trace: 1 Swiggy Biryani Order = 9 Concepts

When a user taps *"Place Order"* on Swiggy, watch the map light up:

```
[ User Phone (Delhi) ]
      │  (1) DNS Resolution (Networking) ──► Finds IP for api.swiggy.com
      ▼
[ Load Balancer (Nginx/ALB) ] (Networking) ──► Distributes load, bypasses dead servers
      │  (2) API Gateway (APIs) ──► Validates JWT Auth & checks Rate Limits (Token Bucket)
      ▼
[ Order Microservice (REST) ] (APIs) ──► Handles request business logic
      │  (3) Redis Cache (Databases) ──► Checks restaurant menu price (DB read avoided)
      ▼
[ PostgreSQL Cluster (ACID) ] (Databases) ──► Writes order row into Sharded DB transaction
      │  (4) Event Queue / Pub-Sub (Distributed) ──► Emits "OrderPlaced" event to:
      │       ├──► Restaurant Merchant App
      │       ├──► Delivery Partner Assignment
      │       └──► Real-Time Analytics
      ▼
[ Payment Gateway Call (Idempotency Key) ] (APIs/Distributed) ──► Double-tap won't double-charge
      │
[ Circuit Breaker (Operations) ] ──► If Bank Gateway hangs, fails fast instead of freezing app!
```

## 🧠 4. The 4 Recurring Senior Architecture Arguments
Senior engineers don't memorize 30 disconnected items; they frame designs using 4 core arguments:

1. **The Freshness Argument (Staleness vs Speed):**  
   * *Where it appears:* Caching TTL, DB Replication Lag, CDN Cache, Eventual Consistency.  
   * *Core Question:* "How many seconds of stale data can the user tolerate in exchange for 10x faster response time?"
2. **The Coordination Argument (Agreement vs Throughput):**  
   * *Where it appears:* Distributed Locks, 2PC vs Sagas, Consensus (Raft), Idempotency.  
   * *Core Question:* "How can we avoid locking servers across a network? (Answer: Use Sagas and Idempotency keys instead of distributed locks)."
3. **The Capacity Argument (Scaling bottlenecks):**  
   * *Where it appears:* Load Balancing, Sharding, Consistent Hashing, Message Queues.  
   * *Core Question:* "When data exceeds 1 machine, how do we slice it without creating hot-spots?"
4. **The Blast-Radius Argument (Failure containment):**  
   * *Where it appears:* Circuit Breakers, Bulkhead pattern, Rate Limiters, Dead Letter Queues (DLQ).  
   * *Core Question:* "When (not if) dependency X goes down, how do we prevent the whole application from crashing?"

## 💥 5. Incident Diagnosis: Real Failures & Root-Cause Mapping

In production outages or system design interview troubleshooting:

```
Incident Symptom                                Probable Territory & Root Cause
─────────────────────────────────────────────   ──────────────────────────────────────────────────────────
🔴 "Site is slow for 100% of global users"      ──► Networking (DNS failure, CDN misconfig, LB health check)
🔴 "Slow for 1 large enterprise customer"       ──► Databases (Hot Shard, missing index on tenant_id column)
🔴 "Users charged twice on flaky 4G networks"  ──► Distributed/APIs (Missing Idempotency Key on payment API)
🔴 "Fast in Staging, dies at 6 PM in Prod"      ──► Capacity (DB Connection Pool exhausted, Cache Stampede)
🔴 "One 3rd-party API down, entire app crashed" ──► Operations (Missing Circuit Breaker / Request Timeout)
```

## 🎯 6. Priority Tiers for Interview Preparation

* **Tier 1 (Master Cold - 80% of Interviews):** Load Balancing, Caching, SQL vs NoSQL, Sharding, Replication, CAP Theorem, Consistent Hashing, Message Queues vs Pub/Sub, Idempotency, REST, Circuit Breakers.
* **Tier 2 (Working Knowledge):** gRPC, Rate Limiting algorithms, B-Tree vs LSM, Sagas, Bloom Filters, Distributed Tracing.
* **Tier 3 (Conceptual Awareness):** Paxos proofs, Vector Clocks, CRDTs, 3-Phase Commit (Know what they are; don't over-index).

## 🚫 7. Top 3 Traps to Avoid
1. ❌ **Alphabetical / Dictionary Learning:** Don't memorize definitions in isolation. Learn how concepts interconnect (e.g., Replication $\rightarrow$ Replication Lag $\rightarrow$ Eventual Consistency $\rightarrow$ CAP Theorem).
2. ❌ **Buzzword Dropping:** Saying *"We will use Kafka, Kubernetes, Redis, and Cassandra"* without matching them to specific scale constraints flags you as junior.
3. ❌ **Single Point of Failure (SPOF) Blindness:** Always state what happens when the Master DB or Cache node crashes.
