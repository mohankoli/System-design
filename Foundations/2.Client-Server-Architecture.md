# Client-Server Architecture Cheatsheet (Interview Quick Revision) 🚀

> **Core Axiom:** The Client handles **presentation (UI)**. The Server handles **truth (business logic, security, state, transactions)**. Never trust data coming from the client!

---

## 🛡️ 1. The Golden Rule: "Never Trust the Client"
*The client (Browser, Mobile App) is in enemy territory (DevTools, Burp Suite, Jailbroken OS).*

* ❌ **Vulnerability:** Passing `totalPrice`, `discount`, or `isPaid: true` in the API request body.
* ✅ **Architecture Solution:** 
  - Client sends only: `item_id` and `quantity`.
  - Server fetches real prices from Database, calculates total, applies coupons, and charges user.
  - Server validates: permissions, inventory availability, and idempotency keys.

---

## 🔄 2. Communication Protocols: REST vs WebSockets vs Long Polling

| Protocol | Connection Model | Latency | Server Cost / Scalability | Best Interview Use Case |
|---|---|---|---|---|
| **REST (HTTP 1.1/2)** | Request-Response (Stateless, closes or reuses TCP) | ~50–200ms | 🟢 Highly scalable (Stateless, cacheable) | CRUD, Payments (PhonePe), Order placement |
| **WebSockets** | Persistent, Full-duplex Bidirectional TCP | <10ms | 🟡 Connection-heavy (Needs Redis Pub/Sub gateway) | Live Stock Tickers (Zerodha), Sports (Dream11), Chat |
| **Long Polling** | Client waits until server has data to return | ~50ms | 🔴 High server connection hold | Legacy notifications / Fallback |
| **SSE (Server-Sent Events)**| Persistent 1-way (Server $\rightarrow$ Client) | <20ms | 🟢 Lightweight push | AI streaming responses (ChatGPT), live score feeds |

## 🏛️ 3. Client Architecture Patterns (Thin vs Thick vs BFF vs Edge)

### A. Thin Client (Server-Side Rendering / SSR)
- **Concept:** Server generates full HTML (Next.js SSR / Django). Client just renders.
- **Pros:** Excellent SEO, ultra-fast First Contentful Paint (FCP), less phone CPU.
- **Cons:** Slower interactive UX, higher server CPU load.
- **Example:** Flipkart product pages & SEO landing pages.

### B. Thick Client (Single Page App / SPA & Mobile)
- **Concept:** React/Flutter client downloads JS bundle, fetches raw JSON from API.
- **Pros:** Rich, app-like snappy UI transitions.
- **Cons:** Heavy first load, SEO challenges.
- **Example:** Swiggy Partner Portal, Web Dashboards.

### C. Backend-For-Frontend (BFF Pattern)
- **Problem:** Mobile on 4G needs 8 fields; Web Dashboard needs 40 fields.
- **Solution:** A dedicated micro-backend per client type that aggregates downstream microservices.
- **Example:** Swiggy Mobile App $\rightarrow$ `Mobile BFF` $\rightarrow$ calls Menu, Ratings, Offers services $\rightarrow$ returns optimized 8-field JSON.

### D. Edge Computing (Cloudflare Workers / Lambda@Edge)
- **Concept:** Runs light logic in 200+ global CDN Points of Presence (PoPs) within ~50ms of user.
- **Example:** Geo-routing, A/B testing, header authorization before hitting core DB.

## ⚡ 4. Stateless HTTP & How Scale Works

```
              ┌───► [App Server 1] ───┐
[Client] ────► [Load Balancer] ──┼───► [App Server 2] ───┼──► [Redis Session / DB]
 (Bearer JWT) └───► [App Server 3] ───┘
```

1. **Why Stateless?** Any server can answer any request. You can spin up 1,000 servers for IPL match without worrying about session affinity.
2. **Where does Auth live?**
   - **JWT (Stateless):** Self-contained, signed token verified with public key.
   - **Centralized Session (Stateful):** Session ID in cookie/header $\rightarrow$ validated against Redis cluster in <2ms.
   - ⚠️ *Anti-Pattern:* Never store user sessions in local server RAM (breaks horizontal scaling).

## 🗄️ 5. Client-Server vs Peer-to-Peer (P2P)

| Dimension | Client-Server | Peer-to-Peer (P2P) |
|---|---|---|
| **Source of Truth** | Centralized Server / DB | Distributed across peers |
| **Consistency & ACID** | 🟢 Easy (Single coordinator for Tatkal/UPI) | 🔴 Extremely hard (Consensus/conflict resolution) |
| **Security & Compliance** | 🟢 Strict (RBI data residency, access logs) | 🔴 Untrusted nodes, piracy risks |
| **Bandwidth & Infra Cost**| 🔴 Company pays all cloud egress | 🟢 Zero central egress (Peers share upload) |
| **Best Used For** | Banking, E-commerce, Ride sharing | BitTorrent, WebRTC media streaming, IPFS |

## ⚠️ 6. Top 5 Interview Traps & Red Flags

1. ❌ **Client-side joins/filters:** Fetching 1,000 raw rows to filter in mobile JS $\rightarrow$ *Fix: Always paginate & filter with SQL indexes on the server.*
2. ❌ **Storing auth tokens in `localStorage`:** Vulnerable to XSS $\rightarrow$ *Fix: Use `HttpOnly, Secure, SameSite` Cookies.*
3. ❌ **Polling instead of Push for real-time:** Polling every 100ms for stock prices $\rightarrow$ *Fix: Use WebSockets with Redis Pub/Sub.*
4. ❌ **Ignoring 4G Flakiness & Network Drops:** *Fix: Implement client-side exponential backoff, retry queues, and idempotent API headers (`Idempotency-Key`).*
5. ❌ **Session sticky routing without centralized cache:** Breaks when a server crashes.

## 🏆 7. Real-World India-Scale Architectures

* **Zerodha Kite:** Split transport — **REST** for trade orders (auditable, ACID) + **WebSockets** for live market ticker ticks.
* **IRCTC Tatkal:** Strict **Thin-server model** — all seat booking logic and concurrency locks stay strictly on central servers to prevent bot tampering.
* **Dream11:** **WebSocket gateway clusters** with Redis Pub/Sub fanout for sub-100ms fantasy score updates to millions of concurrent users during IPL.
