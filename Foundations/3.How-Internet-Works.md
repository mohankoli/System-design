# How the Internet Actually Works (System Design & Networking Mastery) 🌐

> **Core Philosophy:** Software cannot beat the speed of light. Latency, outages, and scaling limits in distributed systems trace directly back to physical infrastructure, BGP routing, DNS lookups, TCP handshakes, and transport protocols.

## ⏱️ 1. The 200ms Journey of a Request (End-to-End Request Lifecycle)

When a user in **Delhi** taps **Swiggy** (servers in **Mumbai** `ap-south-1`):

```
[ Delhi Phone ] 
     │  (1) DNS Resolution (~20–50ms cold / ~1ms cached)
     ▼
[ Local ISP / Jio / Airtel ]
     │  (2) Fiber backbone via NIXI (National Internet Exchange of India)
     ▼
[ CDN Edge Node (Delhi / Noida) ] ────► Serves static images / CSS / JS (<10ms)
     │  (3) Dynamic API Request (Live menu, cart, pricing)
     ▼
[ TCP 3-Way Handshake + TLS 1.3 Handshake ] (~20–40ms RTT)
     ▼
[ Swiggy API Gateway (Mumbai) ]
     │  (4) Internal microservice routing & DB query
     ▼
[ PostgreSQL / Redis (Mumbai) ] 
     │  (5) Response payload returned (JSON)
     ▼
[ Delhi Phone ] ───► Total Cold Request Time: ~100–200ms
```

## 🗺️ 2. The Core Network Layers Explained

### A. DNS (Domain Name System) — The Internet's Phonebook
* **What it does:** Translates human-readable names (`swiggy.com`) into IP addresses (`103.248.128.1`).
* **Transport:** Uses **UDP Port 53** by default (fast, single packet, zero handshake).
* **Caching & TTL:** DNS records have a **TTL (Time-To-Live)**:
  - High TTL (e.g., 24 hrs): Great for caching, terrible for emergency IP failovers.
  - Low TTL (e.g., 60s): Fast failover, but adds frequent DNS resolution latency.
* **Anycast DNS:** Multiple global servers share the exact same IP (e.g., Cloudflare `1.1.1.1` or Google `8.8.8.8`). BGP routes the user to the geographically nearest server.

---

### B. TCP vs UDP (Reliability vs Speed)

```
       TCP (Connection-Oriented)                  UDP (Connectionless / Fire-and-Forget)
Client                      Server           Client                      Server
  │ ──── SYN (Seq=x) ─────►   │                │ ──── Packet 1 ─────────►   │
  │ ◄─── SYN-ACK (Ack=x+1) ── │                │ ──── Packet 2 (Dropped) ─► ❌ (Ignored)
  │ ──── ACK (Ack=y+1) ───►   │                │ ──── Packet 3 ─────────►   │
  │ ──── Actual Data ─────►   │                
```

| Feature | TCP (Transmission Control Protocol) | UDP (User Datagram Protocol) |
|---|---|---|
| **Delivery Guarantee** | ✅ Guaranteed delivery & packet ordering | ❌ Best-effort, packets can be dropped/out-of-order |
| **Connection Setup** | 3-Way Handshake (1 RTT latency overhead) | Zero handshake, sends data instantly |
| **Flow & Congestion Control**| ✅ Adjusts speed based on network congestion | ❌ None (Client blasts packets at full speed) |
| **Head-of-Line (HoL) Blocking**| ❌ If packet 2 drops, packet 3 waits in buffer | ✅ None (Moves immediately to next frame) |
| **Best System Design Use** | REST APIs, Payments, Order Cart, Web Pages | Live Video Streaming, Multiplayer Gaming, DNS |

---

### C. HTTPS & TLS (Transport Layer Security)
* **What it does:** Encrypts communication over TCP so eavesdroppers on public Wi-Fi cannot steal cookies or tokens.
* **Handshake Cost:**
  - **TLS 1.2:** Adds **2 RTTs** (Round Trips) before application data can flow.
  - **TLS 1.3:** Adds **1 RTT** (or **0-RTT** with session resumption / pre-shared keys).
* **Interview Insight:** Total cold connection cost = `1 RTT (TCP)` + `1 RTT (TLS 1.3)` = **2 Full Round Trips** before sending `GET /api`.

---

### D. Evolution of HTTP: HTTP/1.1 vs HTTP/2 vs HTTP/3 (QUIC)

```
HTTP/1.1 (Head-of-line blocking per TCP connection)
[ Request 1 ──► Response 1 ] ──► [ Request 2 ──► Response 2 ] (Serial)

HTTP/2 (Multiplexing over single TCP connection)
[ Req 1 Stream ] ──┬──► Interleaved over Single TCP Pipe ──► Processed in Parallel
[ Req 2 Stream ] ──┘

HTTP/3 (QUIC over UDP - Eliminates TCP Head-of-line blocking completely)
[ Stream 1 (UDP) ] ──► Packet drops on Stream 1 do NOT block Stream 2!
```

* **HTTP/1.1:** 1 request per TCP connection at a time. Browsers had to open 6 parallel TCP connections per domain (wasteful handshakes).
* **HTTP/2:** Single TCP connection with **Multiplexing** (multiple requests interleaved as binary streams). Major win for pages with 30+ assets.
* **HTTP/3 (QUIC):** Runs on **UDP** instead of TCP. Eliminates TCP head-of-line blocking caused by packet loss over flaky mobile 4G/5G networks.

## ⚡ 3. The Physical Internet & Latency Realities

### Physics Sets the Latency Floor
The speed of light in fiber optic glass is ~**200,000 km/s**:
* **Mumbai $\rightarrow$ Singapore (~2,700 km):** ~27ms round-trip (practical ~40–50ms).
* **Mumbai $\rightarrow$ London:** ~120ms round-trip.
* **Mumbai $\rightarrow$ California:** ~180–220ms round-trip.

> **Rule:** No amount of code or database tuning can fix a 200ms speed-of-light penalty. If Indian users need sub-50ms latency, your backend must live in `ap-south-1` (Mumbai) or edge caches.

## 💥 4. Real-World Production Failures & Outages (Must-Know for Interviews)

### Failure 1: The BGP Hijack / Route Leak Catastrophe
* **Mechanism:** BGP (Border Gateway Protocol) runs on trust without built-in crypto verification. If an ISP advertises *"I own Google/Cloudflare's IP range"*, global routers believe it and route traffic into a black hole.
* **Real Outage:** Small ISPs have accidentally leaked routes, taking major global platforms down worldwide for hours.
* **Mitigation:** Cloud providers use **RPKI** (cryptographic route validation) and establish peering across multiple **IXPs (Internet Exchange Points)** like NIXI in India.

### Failure 2: Undersea Fiber Cable Cut (The Red Sea / Egypt Incident)
* **Incident:** 99% of global internet traffic travels through undersea fiber cables on the ocean floor. Cargo ship anchors have severed cables near Egypt.
* **Impact:** Indian traffic to Europe had to reroute across the Pacific, adding **+80ms latency** overnight.
* **Architecture Lesson:** Multi-region failover and CDN edge caching are critical disaster recovery mechanisms.

### Failure 3: The 24-Hour DNS TTL Migration Disaster (NPCI / Banking Outage)
* **Failure:** A banking service set their DNS record TTL to `86400` (24 hours) and performed a datacenter IP migration.
* **Impact:** When the old server was decommissioned, millions of users continued hitting the stale IP address for 24 hours. Transactions failed for hours.
* **Best Practice:** Lower DNS TTL to **60–300 seconds** *days before* a scheduled migration; raise it back after stability.

### Failure 4: Hotstar IPL Live Stream TCP Stutter Catastrophe
* **Failure:** If video frames are transmitted over strict TCP, a single dropped packet forces the player to pause and wait for retransmission (**Head-of-line blocking**).
* **Solution:** Video streaming uses **UDP / HLS / DASH over CDN chunks**. If a video packet drops, the decoder skips it rather than buffering for 10 crore concurrent viewers.

### Failure 5: IRCTC Tatkal 10 AM TCP+TLS Handshake Storm
* **Failure:** At 10:00 AM sharp, millions of users hit the site simultaneously. If every connection requires a fresh 3-way TCP handshake + TLS negotiation, Load Balancers crash before processing any SQL queries.
* **Solution:** Pre-warm connection pools, enable **HTTP/2 with Keep-Alive connection reuse**, and offload static UI assets to CDN edge nodes.

## 📊 5. Architecture Decision Matrix

| Scenario / Requirement | Recommended Protocol | Why? | Real-world Indian System |
|---|---|---|---|
| **Payment Confirmation / Auth** | **TCP + TLS 1.3 + HTTP/2** | Guaranteed delivery, encrypted, multiplexed | PhonePe / Razorpay UPI flow |
| **Live Cricket Streaming** | **UDP / QUIC / HLS on CDN** | Frame skipping > Retransmission stutter | Hotstar live IPL streaming |
| **Domain Name Lookup** | **UDP (Port 53)** | Lightweight, single packet, lowest overhead | Initial `swiggy.com` resolve |
| **Static Images / CSS / JS** | **CDN Edge + HTTP/2** | Terminates connection close to user (<10ms) | Flipkart Big Billion Day assets |
| **Live Stock Price Updates** | **WebSocket over TCP** | Persistent, ordered push without polling | Zerodha Kite Tickers |

## 🚫 6. Top 4 Common Engineering Mistakes

1. ❌ **Blaming the Database first:** Profiling SQL for weeks when the real delay was a 300ms un-cached DNS lookup or static assets hosted in US region.
2. ❌ **Assuming "HTTPS = Safe Website":** HTTPS only guarantees **encryption in transit**, not that the website isn't a phishing scam.
3. ❌ **Opening multiple TCP connections in HTTP/1.1:** Causes connection exhaustion on load balancers. *Fix: Use HTTP/2 multiplexing.*
4. ❌ **Ignoring mobile 4G packet loss:** Designing chat/games for stable fiber broadband instead of high-jitter mobile networks. *Fix: Use UDP/QUIC or WebSocket auto-reconnects with exponential backoff.*
