# System Design Interview Mastery Cheatsheet 🚀

> **Core Philosophy:** System design is **not** about knowing all tools (Kafka, K8s). It is **decision-making under constraints**. Never draw a box without asking questions first!

---

## 🎯 1. First 5 Minutes: Clarifying Questions (Must-Ask)
*Never start drawing immediately. Ask these first:*
1. **Functional Scope:** What are the top 2-3 core features? What are we deliberately *not* building?
2. **Scale & Traffic:** 
   - Daily Active Users (DAU) & Peak QPS (Queries per second).
   - Read vs. Write ratio (e.g., Read-heavy 100:1 vs. Write-heavy 1:1).
3. **Latency & SLA:** Latency requirements (e.g., p99 < 100ms) & Availability (99.9% vs 99.99%).
4. **Constraints:** Budget, timeline, compliance/data residency (e.g., GDPR / RBI).

---

## ⚖️ 2. The 4 Forces / Constraints Framework
*Every architecture decision balances these 4 forces:*

```
             [ Architecture Choice ]
           /            |          \
   💰 Budget        ⏱️ Time       👥 Scale       🛠️ Team Skill
 (Cloud cost)    (Speed to ship) (QPS/Storage)  (Ops/Maintenance)
```

- **Budget:** Can we afford managed services, or must we run single VM?
- **Time to market:** Shipping with monolith in 2 weeks > Over-engineered microservices in 3 months.
- **Scale:** 1k users vs 100M users have completely different "correct" answers.
- **Team skill:** If nobody knows Cassandra/K8s at 3 AM, don't use it!

---

## 🪜 3. Step-by-Step Scaling Ladder (How to Evolve Your Design)
*Start simple, then scale as bottlenecks appear:*

1. **Step 1 (Single Box):** App Server + SQL Database (Postgres) on single VM.
2. **Step 2 (Separate DB & App):** Dedicated App Server + Dedicated DB.
3. **Step 3 (Horizontal Scaling):** Load Balancer (Nginx/ALB) + Multiple Stateless App Servers.
4. **Step 4 (Read Bottleneck):** Add Cache layer (Redis/Memcached) + DB Read Replicas.
5. **Step 5 (Static Content):** CDN (Cloudflare/CloudFront) + Object Storage (S3).
6. **Step 6 (Write Bottleneck & Async tasks):** Message Queues (RabbitMQ/Kafka) for background jobs.
7. **Step 7 (Database Scaling):** Database Sharding (Horizontal Partitioning) + Federation.
8. **Step 8 (Global Scale):** Multi-region deployments with geo-DNS routing.

---

## 🔍 4. The 4-Question Method (Evaluating Any Technology)
*Before saying "Let's use Kafka / Redis / NoSQL", answer these:*
1. **What specific problem does it solve today?** (Do we actually have this bottleneck?)
2. **How does it work under the hood?** (e.g., Kafka = append-only log on disk; Redis = in-memory key-value).
3. **When does it break catastrophically?** (Cliff: row lock contention, memory exhaustion, split-brain).
4. **What is the trade-off?** (e.g., Eventual consistency, network latency, operational overhead).

---

## 📊 5. Quick Decision Matrix for Common Scenarios

| Scenario / Constraint | Best Approach / Technology | Reason / Trade-off |
|---|---|---|
| **Early Startup / MVP** | Monolith + Postgres + Managed Auth | Fast shipping, low cost, easy to debug |
| **Financial / Payments / Orders** | Relational DB (Postgres/MySQL) + ACID | Strong consistency, zero lost transactions |
| **High Read, Low Write (e.g., Product Catalog)** | Redis Cache + DB Read Replicas | Blazing fast reads, offloads DB |
| **Massive Spikes (e.g., Live Voting / Flash Sale)** | In-Memory Buffers / Queue + Rate Limiter | Absorbs peak writes without crashing DB |
| **Time-Series / Analytics Logs** | Append-only DB (ClickHouse / TimescaleDB) | Fast continuous ingestion & aggregations |
| **Unstructured / Fast-changing Schema** | Document DB (MongoDB / DynamoDB) | Flexible schema, partition-key scaling |

## 💡 6. Real-World Counter-Examples (To Impress the Interviewer)
- **WhatsApp:** Handled 450M users with ~35 engineers using simple Erlang + FreeBSD.
- **Instagram:** Scaled to 30M users with just 13 engineers using Django + Postgres monolith.
- **Shopify:** Processes billions in GMV using a single modular Ruby on Rails monolith.
- *Key Takeaway:* Scale doesn't require complexity worship; it requires knowing your true bottleneck.

---

## 🚫 7. Top 5 Red Flags in Interviews (What NOT to Do)
❌ **Jumping into boxes immediately** without asking traffic/QPS.  
❌ **Blindly copying Big Tech** (*"Netflix does it, so we should too"*).  
❌ **Choosing tools for resume value** (using Kafka when a DB table with `processed_at` works).  
❌ **Ignoring failure scenarios** (not explaining what happens when DB/Cache/3rd-party API goes down).  
❌ **Not stating trade-offs** (claiming a solution has "no downside").

---

## 🏆 8. Master Formula for Explaining Any Design
> *"Given our constraint of **[Scale / Time / Budget]**, I chose **[Technology X]** because it gives us **[Benefit A]**. The trade-off is **[Disadvantage B]**, which we mitigate by **[Strategy C]**."*
